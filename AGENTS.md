# AGENTS.md

Этот файл фиксирует ожидания к агентам и разработчикам для проекта `guessboss` после перехода публичного сайта на `Nuxt 4`.

## Общие правила

- Основной package manager проекта: только `npm`.
- Использование `pnpm`, `yarn`, `bun` запрещено.
- Все команды установки, запуска, линтинга, typecheck и сборки должны выполняться через `npm`.
- Если требуется одноразовый CLI из npm-экосистемы, использовать только `npm exec` или `npx`, без перехода на другой package manager.

## Обязательные команды

Проект должен поддерживать и использовать следующие команды:

- `npm install`
- `npm run dev`
- `npm run build`
- `npm run lint`
- `npm run lint:fix`
- `npm run typecheck`

## Запуск локального сервера

Агент не должен самостоятельно запускать dev/preview серверы проекта (`npm run dev`, `npm run dev:site`, `npm run preview` или аналогичные долгоживущие команды).
Если для проверки требуется поднять сайт в браузере, агент должен сначала написать владельцу проекта и дождаться явного разрешения.

Разрешено без отдельного согласования запускать конечные проверочные команды, которые завершаются сами: `npm run lint`, `npm run typecheck`, `npm run build` и точечные проверки через `npm exec`/`npx`.

### Когда запускать build

- Для небольших изменений UI, стилей и клиентского поведения `npm run build` по умолчанию не запускать.
- Для таких изменений достаточно обязательных `npm run lint` и `npm run typecheck`, если нет отдельного запроса владельца проекта.
- `npm run build` запускать для значимых архитектурных изменений, изменений зависимостей, конфигурации сборки, серверного слоя или деплоя, а также по прямому запросу владельца проекта.

Изменение считается незавершённым, если после него не проходят:

- `npm run lint`
- `npm run typecheck`

## Архитектурная модель

Проект состоит из трёх отдельных зон:

1. Новый публичный сайт на `Nuxt 4`
2. Серверный слой `Nitro` / `Nuxt server`
3. Существующая админка в `src/admin/`

Legacy-код публичного Express-сайта хранится в `migration_old/` и используется только как источник для переноса.

## Границы ответственности

### Публичный сайт

- Новая публичка строится на `Nuxt 4`.
- Архитектурный подход: feature-based design.
- Новая публичка использует `Tailwind CSS 4`.
- Новый публичный слой не использует BEM как основную методологию.
- Допускаются только небольшие локальные semantic wrappers поверх utility-классов, когда это реально уменьшает дублирование.

### Админка

- Админка остаётся в `src/admin/`.
- Админка не переносится в Nuxt в рамках миграции публичного сайта.
- Админка считается отдельным клиентом backend-слоя.
- Нельзя ломать маршруты `/admin`, `/admin/*`, `/api/auth/*`, `/api/admin/*`.

### Сервер

- Новый серверный слой строится на `Nitro`.
- Prisma остаётся основным доступом к БД.
- Все серверные изменения должны учитывать совместимость с админкой.
- Переменные окружения из legacy `migration_old/server/config.ts` должны быть перенесены в `runtimeConfig` Nuxt без потерь и без произвольного переименования бизнес-смысла.
- Для сессий допустим bridging:
  - legacy `SESSION_SECRET`
  - Nuxt `NUXT_SESSION_PASSWORD`
  - новый слой должен уметь читать `NUXT_SESSION_PASSWORD || SESSION_SECRET`

## Структурные ожидания

Предпочтительная структура нового публичного слоя:

- `app/features/*` — предметные фичи
- `app/shared/*` — общие UI, утилиты, типы
- `app/layouts/*` — layout-уровень
- `app/pages/*` — маршруты и композиция страниц
- `server/api/*` — API handlers
- `server/routes/*` — route handlers
- `server/utils/*` — серверные утилиты

Не следует:

- переносить EJS или legacy DOM-структуры 1:1 без декомпозиции
- копировать legacy CSS целиком в новый слой
- смешивать код админки с публичными фичами

## Styling rules

- Для новой публички использовать `Tailwind CSS 4`.
- Подключение Tailwind 4 должно идти через `@tailwindcss/vite`.
- Глобальный CSS публички начинается с `@import "tailwindcss";`.
- BEM не использовать как стандарт для нового кода публичного сайта.
- Tailwind utility-first — основной способ сборки интерфейса.
- Для CTA-ссылок публичного сайта, которые визуально выглядят как кнопки и ведут через `NuxtLink`, использовать `app/shared/ui/buttons/ButtonLink.vue`.
- `ButtonLink.vue` уже содержит встроенные варианты стрелки (`badge`, `mark`, `none`); не создавать отдельный `ArrowText`/`ActionArrow` для таких кнопок.
- Не использовать `ButtonLink.vue` для полноразмерных карточек-ссылок и декоративных стрелок внутри карточек, где нужна локальная композиция и позиционирование.

## Lint и typecheck

Для Nuxt-части проекта ожидается:

- `@nuxt/eslint`
- `eslint`
- `typescript`
- `vue-tsc`

Базовые ожидания:

- линтер покрывает `app/`, `server/` и при необходимости `src/admin/`
- `typecheck` запускается через `nuxt typecheck`
- сборка не считается достаточной заменой `typecheck`

## Совместимость с админкой

При любых серверных изменениях сохранять:

- `/api/auth/login`
- `/api/auth/logout`
- `/api/auth/me`
- весь набор `/api/admin/*`
- статическую раздачу собранной админки под `/admin`
- SPA fallback для `/admin/*`

## Legacy aliases

При переносе публичного сайта сохранять URL-совместимость:

- `/companies` — канонический публичный маршрут компаний
- `/businesses` — legacy alias, который должен продолжать работать
- все ссылки и редиректы на слой компаний должны оставаться совместимыми с обоими путями, пока alias явно не будет снят отдельной миграцией

Допустимое изменение:

- разовый релогин после смены session-механики

Недопустимо:

- менять URL admin API без отдельной согласованной миграции
- менять shape JSON-ответов без необходимости
- переносить админку на другой стек внутри этой миграции

## Definition of done

Любое значимое изменение в новом публичном слое должно:

- соответствовать feature-based structure
- не нарушать совместимость админки
- проходить `npm run lint`
- проходить `npm run typecheck`
- по возможности проходить `npm run build`

Если какое-то из этих условий не выполнено, это должно быть явно отмечено в итоговом отчёте.
