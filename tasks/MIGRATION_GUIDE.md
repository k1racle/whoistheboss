# Руководство по переносу публичных страниц

Этот документ фиксирует практические правила переноса публичного сайта на Nuxt 4. Он дополняет общую архитектурную документацию и помогает не смешивать новый дизайн, legacy-разметку и backend-контракты.

## Главный принцип

Новая публичная страница не является переписанной EJS-страницей. Мы собираем её заново из Nuxt/Vue-компонентов по актуальному дизайну, сохраняя необходимые данные, URL и серверные контракты.

У legacy-страницы и нового дизайн-макета разные роли:

| Источник | Для чего использовать | Для чего не использовать |
| --- | --- | --- |
| `tasks/html/*` | Визуальная композиция, размеры, порядок блоков, типографика, цвета, адаптивное поведение и интерактив | Backend-архитектура и окончательная компонентная структура |
| `migration_old/server/views/*` | Список данных, бизнес-смысл полей, ссылки, формы, условная видимость и существующие backend-возможности | DOM-структура, BEM-классы, старый дизайн и готовая Vue-архитектура |
| `server/api/*` и типы feature-слоя | Актуальные контракты данных | Источник визуального решения |
| существующие компоненты `app/features/*` и `app/shared/*` | Переиспользуемые секции, карточки, формы, layout и поведение | Причина насильно подгонять новую секцию под неподходящий компонент |

## Сначала HTML, затем точечная сверка с legacy

Структуру страницы и её визуальный стиль в первую очередь берите из актуального HTML-источника в `tasks/html/`. Сначала зафиксируйте только те секции, элементы, состояния и адаптивные варианты, которые действительно присутствуют в эталонном HTML.

После этого можно посмотреть legacy-стили для конкретного элемента, если этот элемент совпадает с элементом из нового HTML-макета. Legacy CSS в таком случае служит дополнительной подсказкой для размеров, поведения или технической реализации, но не меняет утверждённую композицию и не имеет приоритета над новым макетом.

Используйте следующий порядок:

1. Найдите страницу и связанные assets в `tasks/html/`.
2. Составьте список реально существующих в HTML секций и элементов.
3. Зафиксируйте их структуру, стиль, состояния и поведение на desktop и mobile.
4. Найдите совпадающий элемент в legacy только при необходимости уточнить реализацию.
5. Используйте подходящий legacy-стиль точечно, если он не противоречит HTML-эталону и правилам нового Tailwind-слоя.
6. Отбросьте все legacy-элементы, которых нет в актуальном HTML и прямых требованиях.

EJS нельзя использовать как каталог дополнительных блоков. Наличие секции, текста, карточки или декоративного элемента в EJS не является основанием добавлять его на новую страницу. Если элемент отсутствует в HTML-эталоне, не переносите и не придумывайте его без отдельного требования.

## Не копировать legacy-структуру

Legacy-код создаёт сильный, но ошибочный соблазн перенести страницу почти без изменений. Такой подход возвращает старый дизайн, старую DOM-иерархию и BEM-структуру, даже если рядом лежит новый эталонный макет.

При переносе запрещено:

- копировать EJS-разметку блок в блок;
- переносить legacy CSS целиком;
- воспроизводить BEM-иерархию как архитектуру нового Vue-кода;
- считать старый порядок DOM-узлов обязательным;
- добавлять старые секции только потому, что они существуют в legacy;
- придумывать новый визуальный стиль вместо воспроизведения утверждённого HTML-макета.

Legacy нужно читать как документацию к данным и поведению. После определения нужных полей следует закрыть legacy-шаблон и строить компонентную карту по актуальному дизайну.

## Tailwind вместо BEM

Новая публичная часть проекта использует Tailwind CSS 4 как основной способ описания интерфейса. При переносе не создавайте новые BEM-слои и не воспроизводите legacy-классы вида `block__element--modifier` как архитектуру Vue-компонентов.

Допускайте только небольшие локальные semantic wrappers, если они действительно уменьшают повторение utility-классов внутри одного компонента. В остальных случаях описывайте состояние, адаптив, отступы, цвета и типографику через Tailwind-классы рядом с разметкой компонента.

## Приоритет источников

При конфликте источников используйте следующий порядок:

1. Прямые требования владельца проекта.
2. Актуальный эталон из `tasks/html/` и связанные с ним файлы.
3. Уже утверждённые компоненты и паттерны нового Nuxt-приложения.
4. Актуальные API и feature-типы.
5. Legacy-шаблоны как справочник по данным и backend-возможностям.

Legacy никогда не должен переопределять новый дизайн.

## Сначала изучить существующие компоненты

Перед созданием секции найдите похожую реализацию в новом приложении. Проверяйте не только название компонента, но и его реальное назначение, props, slots, мобильную версию и интерактив.

Порядок проверки:

1. Найдите существующие компоненты по смыслу секции.
2. Сравните их с эталонным HTML-макетом.
3. Переиспользуйте компонент без изменений, если контракт полностью подходит.
4. Расширьте компонент типизированными props или slots, если это не ломает его основное назначение.
5. Создайте отдельный feature-компонент, если существующая реализация содержит неподходящую механику.

Не следует переиспользовать компонент только из-за похожего названия. Например, сложная scroll-сцена с pin-анимацией не подходит для простой статичной сетки карточек. В таком случае общую карточку можно сохранить, а контейнер секции нужно сделать отдельным.

## Проверка без самостоятельного запуска сервера

Во время миграции агент не запускает dev/preview сервер самостоятельно. К долгоживущим командам относятся `npm run dev`, `npm run dev:site`, `npm run preview` и любые аналогичные команды, которые поднимают локальный сайт.

Если визуальная проверка требует открытого сервера или браузера, агент сначала пишет владельцу проекта, какая проверка нужна, и ждёт явного разрешения. До этого используются только конечные проверки: `npm run lint`, `npm run typecheck`, `npm run build`, а также точечные команды через `npm exec`/`npx`, если они завершаются сами.

## Первая секция и `FullPage`

Первая секция обычной публичной страницы почти всегда использует общий `FullPage` через `LandingHeroSection`. Меняется прежде всего текст заголовка.

Базовый вариант:

```vue [PageFeature.vue]
<LandingHeroSection title="Кто здесь главный?" />
```

Правила первой секции:

- используйте `FullPage`, чтобы сохранить общую высоту, прокрутку к следующей секции и поведение относительно header;
- используйте общий `LandingHeroSection`, если различается только заголовок;
- передавайте обычный статичный текст без литералов `\n`, если дизайн не требует управляемого переноса;
- не создавайте новую hero-разметку для каждой страницы без визуальной причины;
- сохраняйте `id="top"` для навигации.

Страницы по slug могут иметь самостоятельный дизайнерский hero. Профиль предпринимателя, карточка компании или статья часто требуют изображения, имени, метаданных или иной композиции. В таких случаях сначала сверяйтесь с отдельным slug-макетом и не подменяйте его стандартным `LandingHeroSection` автоматически.

## Статический текст и переносы строк

Текст, который является частью стабильного дизайна, не нужно без необходимости загружать из backend. Это особенно важно для заголовков общих CTA и постоянных пояснений.

Используйте обычные строки:

```vue
<LandingContactSection
  cta-title="Стать участником"
  form-title="Заполните ваши данные для связи"
/>
```

Не записывайте `\n` в строку только для визуального переноса. Браузер должен переносить обычный текст по доступной ширине. Управляемый перенос допустим только тогда, когда он явно является частью утверждённой композиции и одинаково проверен на нужных разрешениях.

## Компонентная структура страницы

Route-файл должен загружать данные, настраивать SEO и передавать готовый контракт feature-компоненту. Route-файл не должен содержать полную верстку страницы.

Feature-страница должна оставаться композицией секций:

```text
app/pages/entrepreneurs/index.vue
  └─ EntrepreneursPage.vue
       ├─ LandingHeroSection
       ├─ EntrepreneursAudienceSection
       │    └─ AudienceCard
       ├─ LandingOurHeroesSection
       │    └─ LandingHeroCard
       ├─ LandingContactSection
       └─ PageBannerSection
```

Выносите компонент, когда элемент:

- повторяется на desktop и mobile;
- используется в нескольких секциях или страницах;
- имеет собственный props-контракт;
- содержит обработку изображения, fallback или интерактив;
- представляет самостоятельный визуальный блок.

## Props и slots

Передавайте данные через типизированные props. Используйте slots, когда родитель управляет композицией заголовка или вводного текста, а дочерний компонент отвечает за сетку и карточки.

Хорошая граница ответственности:

- секция управляет контейнером и раскладкой;
- карточка отвечает за собственное отображение;
- feature-страница передаёт контент;
- route-файл передаёт данные feature-странице.

Не встраивайте page-specific текст внутрь общего компонента, если компонент должен использоваться в нескольких контекстах.

## Карточки и изображения

Карточка изображения должна работать до добавления всех медиафайлов. Реализация должна показывать предсказуемую заглушку, а не пустое прозрачное место.

Для карточек используйте:

- локальный skeleton или нейтральный фон под изображением;
- `/images/placeholder.svg`, если URL отсутствует;
- обработчик ошибки загрузки, который заменяет битый URL на placeholder;
- пустой `alt` для декоративной hover-картинки;
- содержательный `alt` для основной картинки.

Если карточка имеет основную и hover-картинку, начальная прозрачность допустима только для hover-слоя. Корневой элемент карточки не должен иметь `opacity-0` без гарантированно работающего механизма появления.

## Анимации добавляются после статичной версии

Сначала секция должна корректно отображаться без анимации. После проверки данных, размеров, адаптива и доступности можно добавлять reveal, pin, slider или hover-переходы.

Перед добавлением анимации проверьте:

- контент виден при отключённом JavaScript;
- начальное состояние не скрывает карточки навсегда;
- `IntersectionObserver` отключается при уничтожении компонента;
- мобильная версия не наследует desktop-смещения;
- `prefers-reduced-motion` получает спокойный вариант;
- ошибка в анимации не делает контент недоступным.

Если reveal-механика ещё не проверена, оставьте карточки видимыми всегда.

## Desktop и mobile используют один элемент

Desktop-сетка и мобильный слайдер должны по возможности использовать один компонент карточки. Контейнер может меняться, но обработка изображения, ссылка, fallback, подпись и hover-состояние не должны дублироваться.

Пример:

```vue
<LandingSlider>
  <LandingHeroCard v-for="hero in heroes" :key="hero.id" :hero="hero" />
</LandingSlider>

<div class="hidden md:grid">
  <LandingHeroCard v-for="hero in heroes" :key="hero.id" :hero="hero" />
</div>
```

## Секции с управляемым порядком

Если API возвращает `sectionOrder` и `sectionVisibility`, сохраните эти возможности. Они относятся к контракту страницы, а не к legacy-дизайну.

Правила:

- `sectionVisibility[key] === false` скрывает секцию;
- неизвестная секция получает безопасный порядок в конце;
- визуальная реализация секции остаётся новой;
- отсутствие настройки не должно скрывать контент.

## Чек-лист переноса страницы

### До реализации

- [ ] Найден актуальный HTML-макет страницы и отдельный макет slug-страницы, если он существует.
- [ ] Структура страницы составлена только из элементов, которые присутствуют в актуальном HTML или прямых требованиях.
- [ ] Legacy-стили проверяются только для элементов, совпадающих с HTML-эталоном.
- [ ] Элементы, существующие только в EJS, исключены из новой страницы.
- [ ] Определены поля и backend-возможности из legacy.
- [ ] Проверены существующие Nuxt-компоненты.
- [ ] Составлена карта route → feature-page → sections → cards.
- [ ] Зафиксировано, какие тексты статичны, а какие приходят из API.

### Во время реализации

- [ ] Route-файл остаётся тонким.
- [ ] Первая обычная секция использует `FullPage`/`LandingHeroSection`.
- [ ] Legacy DOM и CSS не копируются.
- [ ] Общие карточки вынесены в компоненты.
- [ ] Desktop и mobile переиспользуют карточку.
- [ ] Изображения имеют skeleton и fallback.
- [ ] Контент виден без reveal-анимации.
- [ ] `sectionOrder` и `sectionVisibility` сохранены, если они входят в API.

### После реализации

- [ ] Страница сверена с эталонным HTML на desktop.
- [ ] Страница сверена с эталонным HTML на mobile.
- [ ] Проверены реальные данные, пустые массивы и битые изображения.
- [ ] Выполнен `npm run lint`.
- [ ] Выполнен `npm run typecheck`.
- [ ] По возможности выполнен `npm run build`.
- [ ] Все ошибки, не относящиеся к текущей странице, явно перечислены в отчёте.

## Типичные ошибки

### Новый дизайн выглядит как legacy

Причина: разработчик использовал EJS как визуальный источник. Вернитесь к `tasks/html/`, сравните секции и пересоберите компонентную карту.

### Общий компонент почти подходит, но тянет лишнюю механику

Причина: переиспользован контейнер вместо визуального примитива. Оставьте общую карточку и создайте отдельную feature-секцию.

### Текст показывает символы `\n`

Причина: строка содержит литеральный обратный слеш или компонент не должен управлять переносами. Передайте обычную строку и разрешите CSS выполнять естественный перенос.

### Карточки существуют в DOM, но не видны

Причина: корневой элемент получил `opacity-0`, а reveal-механика не перевела его в видимое состояние. Удалите начальное скрытие до полноценной проверки анимации.

### Tailwind сообщает о TypeScript как о CSS-декларации

Проверьте границы `<script>`, `<template>` и `<style>`. Если SFC уже не содержит style-блока, а ошибка ссылается на виртуальный URL `?vue&type=style`, перезапустите `npm run dev`: Vite мог сохранить удалённый style-модуль в HMR-кэше.
