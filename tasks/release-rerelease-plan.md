# План ререлиза публичного сайта

Статус: исследование шагов 1 и 2 выполнено по репозиторию 7 августа 2026 года. Владелец сообщил, что push в `main`, вероятно, запускает production-деплой автоматически, а рабочих бэкапов PostgreSQL и uploads сейчас нет. Точный механизм автодеплоя и имена production volumes ещё нужно подтвердить у ответственного за инфраструктуру.

## Цель

Перевести production с legacy Express-сайта на Nuxt 4 без потери данных, сохранив работающую админку и закрыв новый публичный сайт сплэш-экраном до официального открытия.

Контент в PostgreSQL и файлы в `public/uploads` считаются невосстановимыми без отдельного бэкапа. Любой production-деплой начинается с проверенной резервной копии обоих хранилищ.

## Неподвижные ограничения

- Использовать только `npm`, `npm exec` или `npx`.
- Не запускать dev- или preview-сервер без разрешения владельца.
- Сохранить `/admin`, `/admin/*`, `/api/auth/*`, `/api/admin/*`, `/companies` и `/businesses`.
- Не запускать seed-команды в production.
- Не удалять и не пересоздавать Docker volumes во время обновления.
- Перед релизом получить успешные результаты `npm run lint`, `npm run typecheck` и, по возможности, `npm run build`.

## 1. Исследование сплэш-экрана и авторизации

### Как работает legacy-версия

Legacy-сайт хранит настройки сплэша в таблице `SiteSetting`:

| Ключ | Назначение |
| --- | --- |
| `SPLASH_ENABLED` | Включает сплэш при строковом значении `true`. |
| `SPLASH_LOGO` | Содержит путь к логотипу, включая загруженный файл из `/uploads`. |
| `SPLASH_MARQUEE` | Содержит текст бегущей строки. |

Админка редактирует эти значения на странице настроек. Express middleware читает их перед обработкой публичных маршрутов и возвращает `splash.ejs` для `GET`-запросов, которые принимают `text/html`.

Middleware пропускает `/admin`, `/api`, `/health`, статику, uploads, robots и sitemap. Поэтому админка, авторизация и API продолжают работать при включённом сплэше.

Сессия legacy-версии:

- хранится в PostgreSQL через `connect-pg-simple`;
- использует cookie `sid`;
- живёт до семи дней;
- содержит `userId`, роль, имя и email;
- использует `SESSION_SECRET` и secure-cookie за production reverse proxy.

### Обнаруженное расхождение

Код production-ветки `main` не пропускает авторизованного администратора на публичные страницы. Сплэш проверяет только URL и флаг `SPLASH_ENABLED`, хотя session middleware уже доступен в этой точке.

Если production сейчас действительно открывает публичный сайт после входа администратора, такое поведение находится вне текущего Git-кода: например, в незакоммиченном изменении на сервере, в отдельном домене, в reverse proxy или в другом способе обхода. Это нужно подтвердить у владельца до реализации.

### Состояние Nuxt/Nitro-версии

Новая версия уже содержит `server/middleware/00.splash.ts`. Middleware повторяет основную legacy-логику:

- читает те же три ключа из `SiteSetting`;
- пропускает `/admin`, `/api`, `/health`, Nuxt assets, uploads, robots и sitemap;
- возвращает самостоятельную HTML-страницу без запуска Vue renderer;
- при ошибке чтения настроек работает fail-open и показывает публичный сайт.

Текущая реализация также показывает сплэш авторизованным `ADMIN` и `EDITOR`. Проверки сессии в splash middleware нет.

### Почему сплэш находится в Nitro, а не в layout

Текущая заглушка является серверным access gate, а не частью интерфейса Nuxt. Nitro middleware выполняется до Vue renderer и может вернуть только сплэш, не создавая HTML и hydration payload закрытой публичной страницы.

Layout-компонент подходит для визуального переключения уже открытого приложения, но сам по себе не закрывает SSR-ответ, Nuxt payload и data fetching. Для дорелизной заглушки серверный middleware надёжнее. Vue-компонент можно добавить только как UI-слой после серверного решения, если сплэшу потребуется сложная интерактивность.

Новая авторизация:

- использует те же записи `User` в PostgreSQL и те же роли;
- создаёт зашифрованную stateless-cookie `nuxt-session` через H3;
- хранит роль внутри зашифрованных session data; браузерный JavaScript не читает её, потому что cookie имеет флаг httpOnly;
- защищает `/api/admin/*` ролями `ADMIN` и `EDITOR`, а управление пользователями — ролью `ADMIN`;
- перенаправляет `ADMIN` и `EDITOR` после входа в `/admin/`;
- использует secure, httpOnly cookie с путём `/`;
- сейчас не задаёт `maxAge`, поэтому cookie является browser-session cookie;
- не читает legacy-cookie `sid`, поэтому один повторный вход после миграции ожидаем и допустим.

### Требуемое изменение перед релизом

Добавить в splash middleware явный preview-bypass для согласованных ролей. Предварительный вариант: пропускать `ADMIN` и `EDITOR`, чтобы контент-мейкеры могли проверять опубликованный результат, но окончательный набор ролей должен подтвердить владелец.

Реализация должна:

1. Сначала проверить метод, тип ответа и исключённые пути.
2. Прочитать `SPLASH_ENABLED`.
3. При включённом сплэше прочитать текущую Nuxt-сессию.
4. Пропустить согласованные роли и вернуть сплэш остальным посетителям.
5. Добавить `Cache-Control: private, no-store` и `Vary: Cookie`, чтобы reverse proxy или CDN не смешивал ответы администратора и гостя.
6. Сохранить доступ к `/admin`, `/api/auth/*`, `/api/admin/*`, статикам и uploads независимо от состояния сплэша.

### Обязательные проверки сплэша

- Гость получает сплэш на `/`, `/companies`, `/businesses` и detail-страницах.
- Гость не получает публичный Nuxt payload вместо сплэша при обычной навигации.
- `/admin/` открывается при включённом сплэше.
- Login, logout и `/api/auth/me` работают при включённом сплэше.
- Авторизованные согласованные роли видят публичный Nuxt-сайт.
- `SUBSCRIBER` и неавторизованный пользователь продолжают видеть сплэш.
- `/uploads/*`, `/_nuxt/*`, `/robots.txt`, `/sitemap.xml` и `/health` доступны.
- Выключение `SPLASH_ENABLED` открывает сайт без перезапуска контейнера.
- Ответы сплэша и preview не кэшируются как общий публичный ответ.
- Смена session secret только разлогинивает пользователей и не затрагивает контент.

## 2. Исследование текущего деплоя

### Что подтверждает репозиторий

История и legacy `README.md` описывают production как Portainer Stack из Git-репозитория с `docker-compose.yml`. В репозитории нет GitHub Actions, release-тегов или отдельного deploy-скрипта.

По информации владельца, push в `main` должен запускать деплой автоматически. Репозиторий не содержит механизма такого запуска, поэтому автоматизация, вероятно, настроена снаружи: через Portainer Git polling, webhook или другую инфраструктуру. До подтверждения этого механизма любой merge или push в `main` считается потенциальным немедленным production-деплоем.

Compose запускает два сервиса:

| Сервис | Данные | Поведение при обновлении |
| --- | --- | --- |
| `app` | Именованный volume `uploads` в `/app/public/uploads` | Контейнер пересобирается из Git. Volume должен подключиться повторно. |
| `db` | Именованный volume `postgres_data` в `/var/lib/postgresql/data` | PostgreSQL использует существующий volume. Контейнер нельзя пересоздавать с новым пустым project/stack name. |

Production-образ собирает админку и Nuxt через `npm run build`, копирует `.output`, Prisma, `public` и entrypoint. При каждом старте entrypoint выполняет `npx prisma generate`, затем `npx prisma migrate deploy`, после чего запускает `node .output/server/index.mjs`.

Seed-команды entrypoint не вызывает. Обычная пересборка app-контейнера не должна менять записи контента или удалять uploads, если Portainer повторно использует те же volumes.

### Состояние миграций

Ветки `main` и `nuxt-migration` содержат одинаковую Prisma schema и одинаковый набор SQL-миграций. Различаются только seed-файлы. Если production уже работает на актуальной `main` и таблица `_prisma_migrations` соответствует репозиторию, переход на Nuxt не должен применять новую schema-миграцию.

Это нужно подтвердить командой `prisma migrate status` на production или на свежем клоне production-базы. Наличие одинаковых файлов в Git не доказывает фактическое состояние production-БД.

### Критический риск runtime environment

Текущий compose передаёт `SESSION_SECRET`, но новая сессия читает Nuxt runtime config. Docker не добавляет service environment на этапе сборки, `.env` исключён из build context, а Nuxt runtime переопределяет ключи через `NUXT_*`.

В текущем виде production-образ может получить пустой пароль сессии. H3 требует пароль не короче 32 символов, поэтому login/session update завершится ошибкой.

Отдельный новый секрет для Nuxt не нужен. На первом Nuxt-деплое нужно передать существующее production-значение `SESSION_SECRET` также под runtime-именем `NUXT_SESSION_PASSWORD`. Это сохраняет один источник секрета и выполняет legacy bridging.

Перед релизом compose должен явно передавать как минимум:

- `NUXT_SESSION_PASSWORD`, используя существующий `SESSION_SECRET` как источник без генерации нового значения перед первым Nuxt-запуском;
- `NUXT_PUBLIC_SITE_URL`;
- `NUXT_PUBLIC_SITE_NAME`;
- `NUXT_PUBLIC_SITE_DESCRIPTION`.

Для совместимости серверный код продолжает читать `NUXT_SESSION_PASSWORD || SESSION_SECRET`, но bridging должен работать именно в runtime-контейнере, а не только во время локальной сборки.

`DATABASE_URL` остаётся рабочим без Nuxt-префикса, потому что Prisma читает её напрямую из `process.env`. Значения `UPLOAD_DIR` и `MAX_UPLOAD_SIZE_MB` сейчас совпадают с собранными defaults, но их runtime-переопределение тоже нужно привести к `NUXT_UPLOAD_DIR` и `NUXT_MAX_UPLOAD_SIZE_MB`, если production использует нестандартные значения.

### Риски сохранности данных

- Рабочих production-бэкапов PostgreSQL и uploads сейчас нет. Это блокирует безопасный merge в `main` до создания и проверки первой пары резервных копий.
- Изменение имени Portainer Stack создаст volumes с другими именами и визуально даст «пустую» базу и uploads.
- Удаление stack вместе с volumes или команда с флагом `-v` уничтожит данные.
- Один `pg_dump` не сохраняет загруженные изображения и видео; нужен отдельный архив uploads.
- Один архив uploads не сохраняет записи и связи из PostgreSQL; нужны обе копии из одной release-точки.
- Автоматический `prisma migrate deploy` запускается до старта приложения. Ошибка миграции оставит новый app-контейнер неработающим, поэтому статус миграций проверяется заранее.
- Rollback к старому приложению после новой необратимой миграции может быть невозможен без восстановления БД. Сейчас schema-дельты между ветками нет, но это нужно перепроверить непосредственно перед деплоем.

### Неизвестные сведения о production

Репозиторий не отвечает на следующие вопросы:

- точное имя Portainer Stack и порождённых им volumes;
- ветка и commit, которые сейчас развёрнуты;
- точный внешний механизм автоматического обновления Stack после push в `main`;
- конфигурация reverse proxy, TLS, CDN и кэширования;
- фактический источник PostgreSQL, если production переопределяет compose;
- место, периодичность и проверяемость бэкапов;
- фактическое состояние `_prisma_migrations`;
- наличие серверных изменений, которых нет в Git;
- допустимое окно простоя и доступ к логам/rollback в Portainer.

## 3. Подготовка релиза

Этот шаг начинается после ответов по production и реализации preview-bypass.

### 3.1. Закрыть блокеры в коде

- Реализовать и протестировать role-aware splash bypass.
- Исправить передачу Nuxt runtime environment в compose.
- Добавить автоматические проверки матрицы «сплэш × роль × маршрут».
- Проверить session cookie за production reverse proxy.
- Проверить сохранение и выдачу новых и старых uploads.
- Зафиксировать известные функциональные расхождения legacy и Nuxt, включая пока не перенесённые email/Telegram-уведомления заявки на съёмку.
- Обновить устаревший `README.md`, который сейчас является шаблоном Nuxt и предлагает запрещённые package managers.

### 3.2. Подготовить release candidate

- Зафиксировать точный commit release candidate.
- Выполнить `npm install`, `npm run lint`, `npm run typecheck` и `npm run build`.
- Собрать Docker image тем же Dockerfile, который использует Portainer.
- Проверить `health`, админку, auth API, admin API, aliases `/companies` и `/businesses`, публичные данные и uploads.
- Проверить включение и выключение сплэша из админки.
- Проверить RC на копии production-БД и копии uploads, если инфраструктура позволяет.

### 3.3. Сделать pre-release backup

- Остановить или кратко заморозить запись контента на согласованное окно, чтобы БД и uploads соответствовали одной точке времени.
- Снять PostgreSQL dump вне database volume.
- Скопировать uploads вне Docker volume.
- Записать commit, дату, stack name, container names, volume names и размеры копий.
- Проверить чтение архива uploads и восстановление dump в отдельную тестовую БД.
- Только после проверки бэкапа разрешить production update.

### 3.4. Выполнить ререлиз под сплэшем

- Убедиться, что `SPLASH_ENABLED=true` до переключения.
- Обновить существующий Stack без изменения его имени и без удаления volumes.
- Дождаться успешного `prisma migrate deploy` и healthy-состояния app.
- Проверить guest splash, admin login, preview, API, записи контента и несколько старых uploads.
- Сравнить контрольные количества ключевых сущностей до и после деплоя.
- Оставить сплэш включённым до отдельного решения об официальном открытии.

### 3.5. Открыть сайт

- Повторить smoke-check публичных страниц через admin preview.
- Выключить `SPLASH_ENABLED` в админке.
- Проверить сайт в гостевом браузере и через внешний HTTP-check.
- Проверить отсутствие закэшированного сплэша.
- Наблюдать health, логи, ошибки API и доступность uploads в согласованный период.

### 3.6. Rollback

- При ошибке приложения вернуть Stack на зафиксированный предыдущий commit, сохранив текущие volumes.
- При повреждении или несовместимом изменении данных сначала остановить запись, затем восстановить согласованную пару PostgreSQL dump и uploads archive.
- Не запускать старое приложение поверх новой несовместимой schema без отдельной проверки.
- Зафиксировать причину rollback и не выключать сплэш до повторного smoke-check.

## 4. Документация релиза и деплоя

После первого проверенного прогона создать `docs/release-and-deployment.md`. Документ должен описывать фактическую, а не предполагаемую инфраструктуру:

- роли и ответственность участников;
- production topology и Portainer Stack;
- список обязательных environment variables без секретных значений;
- точный процесс сборки и обновления;
- preflight и backup;
- Prisma migrations;
- smoke-check под сплэшем;
- официальное открытие сайта;
- rollback приложения и данных;
- проверку восстановления бэкапа;
- troubleshooting для auth, health, database и uploads;
- release log с commit и временем каждого деплоя.

## Критерий готовности к production update

Production update запрещён, пока остаётся хотя бы один пункт:

- неизвестны имена и состояние production volumes;
- нет проверенной пары backup database + uploads;
- не подтверждён deployed commit и Prisma migration status;
- не исправлена передача `NUXT_SESSION_PASSWORD`;
- не согласованы роли preview-bypass;
- не проходят lint, typecheck и build;
- не проверены rollback и smoke-check под включённым сплэшем.
