# Безопасная интеграция Nuxt Image

Статус: `waiting-owner`. Повторную интеграцию нужно начинать только после отдельного согласования и проверки одного компонента в production Docker.

## Цель

Подключить обработку изображений через `@nuxt/image`, не меняя существующие URL в базе данных и не перезагружая файлы через админку. Интеграция должна уменьшить сетевой вес изображений, добавить responsive-варианты и сохранить работу всех ранее загруженных файлов из Docker volume.

## Зачем Nuxt Image нужен проекту

Админка сохраняет изображения как исходные файлы в `public/uploads`. Текущий upload handler не создаёт несколько размеров и не конвертирует изображения в современные форматы. Контент-мейкер может загрузить крупный JPEG или PNG, после чего браузер получает оригинальный файл даже в небольшой карточке.

Nuxt Image может дать проекту следующие преимущества:

- конвертировать JPEG и PNG в WebP, а после отдельной проверки — в AVIF;
- отдавать карточкам уменьшенные варианты вместо полноразмерных оригиналов;
- генерировать `srcset` и выбирать размер изображения под ширину экрана;
- уменьшить объём передаваемых данных и ускорить отображение карточек и первых экранов;
- уменьшить потенциальное влияние изображений на LCP;
- централизовать качество, форматы и набор допустимых размеров;
- кэшировать производные варианты изображений на уровне IPX и reverse proxy.

Сам модуль не гарантирует весь этот эффект после простой замены тега. Компоненты должны получить корректные `width`, `height` или `sizes`, правила качества и приоритет загрузки. Иначе интеграция добавляет IPX-прокси, но не использует его возможности полностью.

Nuxt Image не требуется для SEO-разметки, sitemap или Open Graph meta. Эти части `@nuxtjs/seo` работают независимо.

## Архитектура изображений

Все контентные изображения загружаются через существующую админку. Внешний CDN и внешние image-host отсутствуют.

База данных хранит относительные URL:

```text
/uploads/photo.jpg
```

Production Compose подключает именованный volume:

```text
uploads → /app/public/uploads
```

Админка записывает файлы в каталог из `UPLOAD_DIR`. Nitro route `server/routes/uploads/[...path].get.ts` читает тот же каталог и обслуживает прямые запросы `/uploads/*`.

## Инцидент первой интеграции

Первая интеграция массово заменила контентные `<img>` на `<NuxtImg>`. Локальные `lint`, `typecheck` и production build прошли, но после production-деплоя контентные изображения перестали отображаться.

Обычный `<img>` формировал прямой запрос:

```text
/uploads/photo.jpg
```

`NuxtImg` с IPX формировал производный URL:

```text
/_ipx/.../uploads/photo.jpg
```

Production-конфигурация IPX использовала файловый корень:

```text
/app/.output/public
```

Поэтому IPX искал исходник здесь:

```text
/app/.output/public/uploads/photo.jpg
```

Файл фактически находился здесь:

```text
/app/public/uploads/photo.jpg
```

IPX не находил исходный файл и возвращал ошибку для `/_ipx/*`. Браузер не переходил автоматически к исходному `/uploads/*`, поэтому изображения исчезли со страниц.

## Корневая причина

Интеграция не учла разделение build-time public assets и runtime uploads:

| Назначение | Путь |
| --- | --- |
| Собранная публичная директория Nitro | `/app/.output/public` |
| Runtime uploads из именованного volume | `/app/public/uploads` |
| Корень поиска IPX по умолчанию в production | `/app/.output/public` |
| Корень существующего upload route | `/app/public` |

URL в базе данных корректны и не требуют миграции. Ошибка находится только в файловой конфигурации IPX.

## Выполненный временный откат

- Все добавленные `<NuxtImg>` возвращены на обычные `<img>`.
- URL `/uploads/*` снова обслуживает существующий Nitro route.
- Пакет `@nuxt/image` остаётся установленным и подключённым.
- Компоненты пока не используют `NuxtImg`.
- SEO-модуль и его настройки не откатываются.

## План решения

### Этап 1. Явно настроить файловый корень IPX

IPX должен читать существующий каталог `/app/public`. URL `/uploads/photo.jpg` тогда разрешается в `/app/public/uploads/photo.jpg`.

Предварительная конфигурация:

```ts [nuxt.config.ts]
const uploadDir = resolve(process.env.UPLOAD_DIR ?? './public/uploads')
const imageRootDir = resolve(uploadDir, '..')

export default defineNuxtConfig({
  image: {
    provider: 'ipx',
    ipx: {
      fs: {
        dir: imageRootDir,
      },
    },
  },

  runtimeConfig: {
    uploadDir,
  },
})
```

Перед реализацией нужно подтвердить итоговое значение `runtimeConfig.ipx.fs.dir` внутри Linux production build. Ожидаемое значение — `/app/public`.

### Этап 2. Проверить IPX без массовой миграции

Оставить все текущие `<img>` без изменений и развернуть только конфигурацию IPX. Такое обновление не должно менять существующее отображение сайта.

После деплоя проверить:

1. Старый прямой URL `/uploads/<existing-file>` возвращает `200`.
2. IPX URL для того же файла возвращает `200`.
3. IPX возвращает корректный `Content-Type`, например `image/webp`.
4. Файл, загруженный через админку после деплоя, сразу доступен напрямую и через IPX.
5. Перезапуск контейнера не удаляет исходные файлы и не меняет их URL.

### Этап 3. Вернуть NuxtImg в один компонент

Первым тестовым компонентом использовать `app/features/interviews/ui/InterviewCard.vue`. Компонент должен сохранить текущие классы, aspect ratio, alt-текст и fallback.

Для теста задать осмысленные responsive-параметры, а не ограничиваться заменой имени тега:

```vue
<NuxtImg
  :src="interview.coverImage || '/images/placeholder.svg'"
  :alt="interview.title"
  width="720"
  height="540"
  sizes="100vw sm:50vw lg:33vw"
  format="webp"
  quality="80"
  loading="lazy"
  class="aspect-[4/3] w-full object-cover"
/>
```

Точные `sizes`, ширину, высоту и качество нужно подтвердить по фактической сетке страницы.

### Этап 4. Проверить один компонент в production

Проверить тестовую карточку на desktop и mobile:

- изображение отображается после первого и повторного запроса;
- запрос идёт через `/_ipx/*` и возвращает `200`;
- браузер получает изображение подходящего размера;
- визуальные размеры, crop и hover-состояния не меняются;
- placeholder работает при пустом `coverImage`;
- старые и новые файлы из админки работают одинаково;
- в логах контейнера нет ошибок IPX или Sharp;
- прямые `/uploads/*` продолжают работать для админки и legacy-кода.

### Этап 5. Выполнить постепенную миграцию

После успешной production-проверки мигрировать изображения небольшими группами:

1. Карточки интервью и блога.
2. Каталоги компаний и предпринимателей.
3. Detail-страницы.
4. Landing и изображения, влияющие на LCP.
5. Сложные `<picture>`, hover-пары и fallback-композиции — последними.

После каждой группы запускать `npm run lint`, `npm run typecheck` и `npm run build`, затем проверять production Network и логи.

## Альтернативное решение через Docker volume

Один и тот же volume можно подключить к двум путям:

```yaml [docker-compose.yml]
volumes:
  - uploads:/app/public/uploads
  - uploads:/app/.output/public/uploads
```

Этот вариант не требует изменения URL или повторной загрузки файлов. Однако явная настройка файлового корня IPX предпочтительнее: она сохраняет один runtime-путь и не дублирует mount point внутри контейнера.

## План отката

Если тестовый компонент снова получает ошибки `/_ipx/*`, вернуть в нём обычный `<img>` и сохранить прямые `/uploads/*`. Не изменять записи базы данных, upload volume и существующие файлы.

## Критерии готовности

- IPX читает существующие файлы из `/app/public/uploads`.
- Миграция не требует перезагрузки или изменения изображений в базе данных.
- Старые и новые файлы из админки доступны через прямой URL и IPX.
- Один тестовый компонент успешно проверен в production до массовой замены.
- Responsive-варианты реально уменьшают передаваемый размер изображения.
- Все изменения проходят `npm run lint`, `npm run typecheck` и `npm run build`.
- В production отсутствуют ошибки IPX, Sharp и ответы `404` для существующих uploads.
