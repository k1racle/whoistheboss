# Спецификация проекта «Маршрут Построен»

Этот документ описывает текущее устройство проекта `guessboss`: публичный сайт, серверный слой, административную панель, модель данных и общие интерфейсные компоненты. Он служит ориентиром для разработки и не описывает legacy-реализацию как актуальную архитектуру.

Если документ расходится с рабочим кодом, источником истины остается код. После изменения архитектуры, публичных контрактов или общего UI этот документ нужно обновить.

## 1. Назначение и границы проекта

Проект состоит из трех самостоятельных зон:

1. Публичный сайт на Nuxt 4.
2. Серверный слой Nitro с Prisma и PostgreSQL.
3. Отдельная административная SPA в `src/admin/`.

Публичный сайт публикует материалы о предпринимателях, компаниях, интервью, статьях и коротких видео. Админка управляет контентом и настройками публичных страниц. Legacy-код в `migration_old/` используется только как справочный источник и не входит в рабочую архитектуру.

## 3. Архитектура

### 3.1. Публичный сайт

Публичный слой построен по feature-based принципу:

- `app/pages/` отвечает за маршруты и композицию страниц;
- `app/features/` содержит предметные блоки страниц;
- `app/shared/` содержит общий UI, layout-компоненты, composables, типы и утилиты;
- `app/layouts/` связывает маршруты с общим layout сайта.

Страницы получают данные на сервере через `useAsyncData` и общий API-клиент `useApi`. Feature-компоненты получают подготовленные данные через props и не должны самостоятельно дублировать запросы страницы без отдельной причины.

### 3.2. Сервер

Серверные обработчики расположены в:

- `server/api/` — JSON API;
- `server/routes/` — обычные route handlers, включая healthcheck и раздачу файлов;
- `server/utils/` — Prisma, авторизация, нормализация контента и другие серверные утилиты.

Prisma остается единственным основным способом доступа к PostgreSQL.

### 3.3. Админка

Админка остается отдельным Vite-клиентом на TypeScript в `src/admin/`. Она формирует HTML-строки, использует browser DOM API и собственный роутер из `src/admin/router.ts`. Админка собирается в `dist/admin` и раздается Nitro под `/admin` с SPA fallback для `/admin/*`.

Админка не импортирует компоненты публичного Nuxt-приложения и взаимодействует с сервером через `/api/auth/*` и `/api/admin/*`.

Подробная карта админки, ее маршрутов и сквозных сценариев изменений находится в `docs/ADMIN.md`.

### 3.4. Основные каталоги

```text
app/
  assets/                 глобальные стили и шрифты
  features/               предметные компоненты публичных страниц
  layouts/                Nuxt layouts
  pages/                  публичные маршруты
  shared/                 общий UI, layout, composables и утилиты
server/
  api/                    публичное, auth- и admin-API
  routes/                 healthcheck, uploads и служебные маршруты
  utils/                  серверные функции и нормализация данных
src/admin/                отдельная административная SPA
prisma/                   схема и миграции базы данных
public/                   публичные статические файлы и uploads
scripts/                  служебные скрипты
migration_old/            архив legacy-реализации
docs/                     проектная документация
```

В `nuxt.config.ts` настроены aliases `@features`, `@shared`, `@server` и `@admin`.

## 5. Композиция и данные публичных страниц

### 5.1. Загрузка данных

Общий composable `useApi` предоставляет SSR-aware методы `request`, `get`, `post`, `put`, `patch` и `del`. На сервере он использует request-aware fetch, а в браузере — `$fetch`.

Страница должна:

1. Получить данные через публичный API.
2. Обработать отсутствие сущности через 404.
3. Передать данные feature-компонентам.
4. Настроить метаданные страницы через `useSeoMeta`, если они нужны маршруту.

### 5.2. Управляемые секции

Для страниц с настраиваемой композицией сервер возвращает:

- видимость секций;
- порядок секций;
- содержимое секций.

Утилиты `parseSectionVisibility` и `parseSectionOrder` безопасно разбирают JSON-конфигурацию, сохраняют значения по умолчанию и игнорируют неизвестные или некорректные элементы.

Публичная страница не должна менять сохраненную конфигурацию. Она только нормализует данные для отображения.

### 5.3. Общий баннер

Баннер управляется централизованно через `useSiteBanner` и `/api/site-banner`. Настройки поддерживают отдельные переключатели для:

- главной;
- каталога и страницы компании;
- каталога и страницы предпринимателя;
- блога и статьи;
- страницы заявки;
- контактов;
- reels;
- списка и страницы интервью.

Компонент страницы размещает `PageBannerSection` между основным контентом и footer. Сам footer находится в общем layout.

## 6. Дизайн-система и стили

### 6.1. Базовые правила

- Публичный сайт использует Tailwind CSS 4 и utility-first подход.
- BEM не используется как основная методология.
- Локальный semantic wrapper допустим, только если он действительно уменьшает повторение.
- Адаптивные стили строятся mobile-first.
- Изменения дизайна должны быть точечными: нельзя попутно исправлять или унифицировать элементы, которых нет в задаче.

### 6.2. Шрифты

В проекте подключены локальные семейства:

- `Dexa Pro` — основной текстовый шрифт, начертания regular и bold;
- `Dexa Pro Condensed` — display-шрифт, начертания regular и black.

Tailwind-токены:

- `font-sans` — `Dexa Pro`;
- `font-display` — `Dexa Pro Condensed`.

### 6.3. Основные цвета

| Токен | Значение | Назначение |
| --- | --- | --- |
| `accent` | `#db2a00` | Красный акцент |
| `background` | `#e5e5e5` | Основной фон |
| `surface` | `#ffffff` | Светлые поверхности |
| `text` | `#070707` | Основной текст |

Максимальная ширина внешней оболочки сайта — `1920px`.

## 7. Каталог общих компонентов

Этот раздел фиксирует назначение компонентов и границы их повторного использования. Перед созданием нового общего компонента нужно проверить существующие контракты.

### 7.1. Layout и навигация

| Компонент | Назначение |
| --- | --- |
| `LayoutMaster` | Ограничивает максимальную ширину приложения и формирует внешнюю оболочку |
| `LayoutDefault` | Собирает header, main и footer; синхронизирует видимость логотипа с маршрутом |
| `SiteHeader` | Sticky-header, desktop-навигация и мобильное меню через Teleport |
| `SiteFooter` | Общий footer с навигацией, social links и CTA |
| `SiteLogo` | Единый вывод логотипа с настраиваемым источником изображения |

`SiteHeader` закрывает мобильное меню при смене маршрута, нажатии Escape и переходе на desktop breakpoint, а также блокирует прокрутку body на время открытого меню.

Composable `useSiteHeader` управляет поведением логотипа. На главной и странице заявки его видимость зависит от прокрутки; на остальных страницах логотип отображается постоянно.

### 7.2. Кнопки и поля

#### `ButtonLink`

`ButtonLink.vue` — общий CTA-компонент на основе `NuxtLink`. Его нужно использовать для ссылок, которые визуально являются кнопками.

| Prop | Значения | Назначение |
| --- | --- | --- |
| `to` | `RouteLocationRaw` | Обязательный маршрут или URL |
| `arrow` | `badge`, `mark`, `none` | Вариант стрелки; по умолчанию `badge` |
| `size` | `md`, `header`, `story` | Размер кнопки |
| `variant` | `flat`, `border`, `invert` | Визуальный вариант |
| `desktopOnly` | `boolean` | Скрывает кнопку на мобильном разрешении |
| `emphasis` | `boolean` | Включает усиленное визуальное выделение |

`ButtonLink` не используется для полноразмерных карточек-ссылок и декоративных стрелок внутри карточек: таким элементам нужна локальная композиция и позиционирование.

#### `InputBasic`

`InputBasic.vue` — общее контролируемое поле с floating label. Поддерживает `v-model`, типы `text`, `tel`, `email`, а также `autocomplete`, `required`, `minlength` и `placeholder`.

### 7.6. Story-секции

`EntrepreneurStorySection` принимает нормализованный объект секции и выбирает один из четырех вариантов.

| Тип | Компонент | Назначение |
| --- | --- | --- |
| `BIOGRAPHY` | `EntrepreneurStorySectionV01` | Биографическая секция с eyebrow, блоками текста и изображением |
| `ACCENT` | `EntrepreneurStorySectionV02` | Красная акцентная текстовая секция |
| `PORTRAIT` | `EntrepreneurStorySectionV03` | Портрет, основной и дополнительный текст |
| `WIDE` | `EntrepreneurStorySectionV04` | Широкое изображение и текстовый блок |

Сервер нормализует story-секции через `server/utils/entrepreneur-story-sections.ts`. Если `storySections` еще не заполнен, нормализатор умеет собрать отображение из legacy-полей. Этот fallback не записывает данные обратно и не затирает содержимое админки.

Story-компоненты используются не только в биографии предпринимателя: варианты `BIOGRAPHY` и `PORTRAIT`, а также общий диспетчер применяются на странице компании. Поэтому изменение их базовых отступов или типографики влияет на оба типа страниц.

## 8. Административная панель

### 8.1. Доступ

Админка использует сессионную авторизацию. Роли:

- `ADMIN` — полный доступ, включая управление пользователями;
- `EDITOR` — управление контентом без административных операций над пользователями.

Нужно сохранять совместимость маршрутов:

- `/api/auth/login`;
- `/api/auth/logout`;
- `/api/auth/me`;
- `/api/admin/*`.

### 8.2. Управляемые сущности и страницы

Админка содержит редакторы и CRUD-интерфейсы для:

- главных настроек страниц предпринимателей, компаний, блога и заявки на съемку;
- предпринимателей;
- компаний;
- интервью;
- reels;
- статей;
- карточек аудитории;
- баннера;
- этапов съемки;
- заявок;
- комментариев;
- подписчиков;
- пользователей;
- системных настроек.

### 8.3. Порядок и видимость секций

Для управляемых страниц админка сохраняет порядок и видимость секций в JSON-полях сущности или в `SiteSetting`. Публичный сервер валидирует и нормализует эти значения перед отдачей.

Новые секции должны иметь безопасное значение по умолчанию, чтобы существующие записи продолжали отображаться без ручного пересохранения.

### 8.4. Истории предпринимателей и компаний

Редактор поддерживает типизированный массив `storySections`. Для компании также доступны дополнительные story-секции и переключатель собственной биографии владельца.

Legacy-поля пока сохраняются для обратной совместимости. Удалять их можно только отдельной миграцией после проверки данных.

### 8.5. Статьи

Статья поддерживает:

- главное и дополнительное изображения;
- произвольный текст источника отдельно для каждого изображения;
- связанные материалы;
- порядок и видимость секций.

Источник изображения хранится как обычный текст. Публичная статья выводит строку `ИСТОЧНИК: ...` только при заполненном поле.

Связанный материал явно различает предпринимателя и компанию. Админка не должна терять тип при сохранении списка.

### 8.6. Безопасность данных при изменении схемы

Добавление nullable-поля или новой настройки не должно изменять существующий контент. Изменения, которые преобразуют или удаляют данные, требуют отдельной миграции и проверки резервной копии.

`prisma migrate deploy` применяет уже созданные миграции и не запускает произвольное пересохранение контента через админку. Риск потери данных определяется SQL конкретной миграции, поэтому destructive-операции нельзя включать в обычную стилевую задачу.

## 9. API

### 9.1. Публичные данные

| `GET /api/companies/:slug` | Страница компании |
| `GET /api/businesses` | Упорядоченные карточки компаний для блока «Места»; поддерживает `limit` и `offset` |
| `GET /api/entrepreneurs-page` | Настройки и данные каталога предпринимателей |
| `GET /api/entrepreneurs/:slug` | Страница предпринимателя |
| `GET /api/blog-page` | Настройки и данные блога |
| `GET /api/blog/:slug` | Статья |
| `GET /api/articles/latest` | Последние статьи |
| `GET /api/interviews` | Список интервью |
| `GET /api/interviews/:slug` | Интервью |
| `GET /api/reels` | Список reels |
| `GET /api/reels/:slug` | Конкретный reel |
| `GET /api/contacts` | Контактные данные |
| `GET /api/shooting-page` | Данные страницы заявки |
| `POST /api/shooting-request` | Создание заявки на съемку |
| `GET /api/site-banner` | Конфигурация общего баннера |

`GET /api/businesses` по умолчанию возвращает первые три опубликованные компании по `Business.placesSortOrder`. Ответ сохраняет массив `businesses` и добавляет объект `pagination` с полями `limit`, `offset`, `hasMore` и `nextOffset`. Каталог `/companies` использует собственную сортировку и не зависит от порядка блока «Места».

### 9.2. Авторизация

| Endpoint | Назначение |
| --- | --- |
| `POST /api/auth/login` | Вход и создание сессии |
| `GET`, `POST /api/auth/logout` | Завершение сессии; поддерживаются переход из браузера и API-вызов |
| `GET /api/auth/me` | Текущий пользователь |
| `POST /api/auth/register` | Регистрация |

### 9.3. Admin API

Catch-all обработчик `/api/admin/[...path]` обслуживает ресурсы:

- `users` — только для `ADMIN`;
- `entrepreneurs`;
- `interviews`;
- `reels`;
- `articles`;
- `businesses`;
- `audience-cards`;
- `comments`;
- `shooting-requests`;
- `subscribers`;
- `settings`;
- `upload`.

Ресурс `businesses` поддерживает `PUT /api/admin/businesses/order`. Endpoint принимает полный массив идентификаторов компаний и транзакционно сохраняет их позиции в `Business.placesSortOrder`.

Менять URL или shape существующих JSON-ответов без отдельной согласованной миграции нельзя.

## 10. Модель данных

Основные Prisma-модели:

- `User`;

- `AudienceCard`;
- `Interview`;
- `Reel`;
- `Article`;
- `Business`;
- `Comment`;

Основные enum-типы:

Структурированный контент нормализуется сервером перед использованием. `storySections` хранится в Prisma JSON-поле. `relatedMaterials`, `sectionVisibility`, `sectionOrder` и блоки собственной биографии владельца компании хранят сериализованный JSON в текстовых полях.

Перед изменением JSON-контракта нужно одновременно проверить:

1. Prisma-модель и существующие записи.
2. Admin API и формы админки.
3. Серверную нормализацию.
4. Типы и отображение публичной страницы.

## 11. Файлы и медиа

Загруженные файлы хранятся в `public/uploads` и раздаются через `/uploads/*`. Сервер валидирует путь к файлу и устанавливает долгий immutable cache для существующих ресурсов.

В Docker Compose каталог uploads подключается как постоянный volume к `/app/public/uploads`.

Статические изображения интерфейса, которые поставляются вместе с приложением, размещаются в `public/images`. Favicon не должен использоваться как источник обычного контентного placeholder: для этого существует отдельный `LogoPlaceholder.svg`.

## 12. SEO и обработка изображений

Публичные страницы задают title, description и social metadata через `useSeoMeta` там, где это реализовано в маршруте. Модули `@nuxtjs/seo` и `@nuxt/image` подключены в `nuxt.config.ts`.

Текущая SEO-конфигурация включает:

- общие данные сайта из `SITE_URL`, `SITE_NAME` и `SITE_DESCRIPTION`;
- русский язык и локаль по умолчанию;
- `robots.txt` с закрытием `/admin`, `/api`, `/login` и `/register`;
- sitemap с динамическими URL опубликованных предпринимателей, компаний, статей и интервью;
- исключение legacy-маршрутов `/businesses` из sitemap;
- базовую Schema.org identity типа `Organization`;
- link checker без остановки сборки при найденной ошибке.

Генерация OG-изображений явно выключена через `ogImage: false`. Ее нельзя считать частью текущего SEO-контракта.

## 13. Конфигурация и переменные окружения

Nuxt `runtimeConfig` содержит серверные настройки для:

- подключения к базе данных;
- session secret;
- uploads;
- SMTP;
- Telegram;
- публичного адреса сайта.

Пароль сессии читается в порядке совместимости:

```text
NUXT_SESSION_PASSWORD || SESSION_SECRET || runtimeConfig
```

Это позволяет сохранить существующие deployment-переменные после перехода с legacy-сервера. Произвольно переименовывать переменные с бизнес-смыслом нельзя.

## 14. Сборка и deployment

### 14.1. Основные команды

```bash
npm install
npm run dev
npm run build
npm run lint
npm run lint:fix
npm run typecheck
```

Дополнительные команды:

```bash
npm run build:admin
npm run preview
npm run generate
```

Dev- и preview-серверы запускаются агентом только после явного разрешения владельца проекта.

### 14.2. Docker

Production image собирается в два этапа:

1. Сборка административной SPA.
2. Сборка Nuxt/Nitro-приложения.

Контейнер запускает `.output/server/index.mjs`. PostgreSQL работает в отдельном контейнере на образе PostgreSQL 16 Alpine. Healthcheck приложения доступен по `/health`.

### 14.3. Миграции Prisma

Текущий `docker-entrypoint` выполняет `npx prisma generate`, но не запускает миграции автоматически. После deployment миграции применяются явной командой внутри контейнера приложения:

```bash
npx prisma migrate deploy
```

Перед запуском нужно убедиться, что команда выполняется в каталоге приложения и использует production `DATABASE_URL`.

## 15. Правила разработки

- Использовать только `npm`.
- Сохранять feature-based структуру Nuxt-приложения.
- Не смешивать публичные feature-компоненты с кодом админки.
- Не переносить legacy EJS/CSS в новую публичку без декомпозиции.
- Использовать Tailwind CSS 4 как основной способ стилизации.
- Для CTA-ссылок использовать `ButtonLink`; не подменять им карточки и локальные декоративные стрелки.
- Не расширять объем точечной дизайн-задачи рефакторингом соседних компонентов.
- Сохранять `/companies` и legacy aliases `/businesses`.
- Сохранять auth- и admin-API без несогласованных изменений URL и JSON-контрактов.
- При серверных изменениях учитывать админку как отдельного клиента.
- Не удалять legacy-поля данных без отдельной миграции и проверки содержимого.

## 16. Definition of done

Значимое изменение считается завершенным, когда:

1. Оно соответствует текущей архитектуре и границам задачи.
2. Публичный сайт, сервер и админка сохраняют согласованные контракты.
3. `npm run lint` завершается успешно.
4. `npm run typecheck` завершается успешно.
5. Для изменений архитектуры, зависимостей, конфигурации, сервера или deployment при необходимости проходит `npm run build`.
6. Изменения общих компонентов, API или модели данных отражены в этой спецификации.

Для небольших правок документации, UI и стилей полный build по умолчанию не требуется. Если обязательная проверка не выполнена или завершается с ошибкой, это нужно явно указать в отчете.
